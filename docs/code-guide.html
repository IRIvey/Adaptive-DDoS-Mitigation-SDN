Code Guide

How the project actually works

What every file does, how four separate pieces of software fit together, what happens during one second of simulated time, and which file to open when you want to change something.

The idea in one paragraph

A simulated network carries normal traffic and a flood. The switch counts every packet and, once a second, describes each traffic flow with six numbers. Those numbers go to the SDN controller, which asks a machine learning model whether each flow looks like an attack. If it does, the controller tells the switch to drop that source, and the flood stops reaching its target. The models are trained beforehand in Python and compiled into the simulator as plain C++.

Four pieces of software, and who does what

Only the last two rows are ours. The rest is existing software we assembled - which is normal, and worth being able to explain.

One second of simulated time

This is the loop that matters. Every box names the file and function that does the work, so you can follow it in the source.

The same thing in words

  1. A host sends a packet. It reaches the switch module's handleMessage().
  2. The switch checks its block list. If that source is blocked on that port, the packet is deleted here and never reaches the victim. This is the mitigation.
  3. Otherwise recordFrame() adds one packet and its bytes to the counters for that flow, where a flow is source and destination address, protocol and ports.
  4. Once a second a timer calls sendStatsReport(), which turns each active flow into six numbers and resets the counters.
  5. Those go to the controller in a DDoSFlowStats message, riding the OpenFlow vendor channel so no change to the OpenFlow model was needed.
  6. The controller emits it as a signal; DDoSDetectorApp receives it and, for each flow, builds a six-element array and calls dtClassify() or kmClassify().
  7. On a verdict of attack it sends a DDoSBlockCommand back with the port and source address.
  8. The switch adds that pair to its block list with an expiry ten seconds later. Step 2 now drops that traffic until the block lapses.

The five detector modes

One parameter in the ini file picks which decision rule runs. All of them use the same two trained models underneath; what differs is how a verdict is reached.

ModeHow it decidesIts parameter
collect Never blocks. Labels each flow from ground truth and writes the training CSV. csvFile
dt Decision Tree only. Blocks when the tree says attack. —
kmeans K-Means only. Blocks when a flow sits further from every normal cluster than the threshold. —
hybrid Tree blocks on sight. K-Means alone must flag the same flow for several consecutive reports first. confirmations
cost Scores both actions and takes the cheaper. See below. falseBlockCost

How the cost rule works

This is expectimax at depth one: rather than thresholding a yes/no, put a price on each action and pick the cheaper. 

p = distance / (distance + threshold)     // K-Means distance as confidence
if the tree says attack:  p = max(p, 0.99)

cost of allowing = p       x bytes this flow will deliver
cost of blocking = (1 - p) x falseBlockCost

block if  cost of allowing > cost of blocking

The left-hand side scales with the flow's own rate, so a loud suspicious flow is blocked on weaker evidence than a quiet one - which is precisely what a fixed threshold cannot express, and why this beats the hybrid where false positives are expensive.

The parameter is not cosmetic

falseBlockCost is measured in bytes, and the scale that matters is the attack's own byte rate. A quiet attack delivers about 14 kB/s, so a penalty of 200,000 demands near-certainty and the rule never fires — it degenerates into the Decision Tree and scores zero. At 30,000 it works well. Always sweep it against the attack you care about rather than trusting a default.

Seeing it happen

When a block is installed, the switch turns the offending host's icon red, pops a BLOCKED 192.168.1.21 bubble, and updates a caption under itself with the number of blocked sources and dropped frames. The colour clears when the block expires. All of it lives in setHostAlarm() and refreshBlockDisplay() in DDoSSwitch.cc, and does nothing when running headless.

The other half: training, which happens beforehand

Nothing above involves Python. The models must already exist as C++ when the simulation starts, so training is a separate pass:

  1. bash run.sh Collect Cmdenv 60s runs the network with the detector in observe-only mode. It writes one CSV row per flow per second, labelled attack if the source is one of the attacker hosts named in the ini file.
  2. python inspect_csv.py checks the dataset — this is what catches a feature that is the same value in both classes and therefore useless.
  3. python train.py fits the Decision Tree on labelled rows and K-Means on the normal rows only, then writes both out as C++ source: src/DecisionTree.h and src/KMeansModel.h.
  4. bash build.sh compiles those headers into the simulator.

The trained Decision Tree is four lines of C++ — a single comparison. K-Means is three centroid coordinates plus a distance check. Neither needs a machine learning library at simulation time, which is exactly why this approach fits inside a C++ simulator at all.

The step people forget

Retraining without running build.sh changes nothing. The model lives inside the compiled executable, not in a file the simulator reads at startup.

Adding a feature touches five files, in this order

ml/schema.py (add the name) → src/DDoSMessages.msg (add the field) → src/DDoSSwitch.cc (measure it, fill it in) → src/DDoSDetectorApp.cc (add it to the feature array and the CSV) → retrain → build.sh.

The order of the features must be identical in schema.py, the message, and the feature array. The generated header refers to them only as f[0] … f[5], so a mismatch will not fail to compile — it will silently feed the model the wrong numbers.

The dataset

It is ours. Nothing was downloaded. The simulator computes the network, so it can also describe it, and because the configuration file says which hosts are attackers, every row's label is known exactly rather than guessed.

What one row looks like

Fourteen columns: time, switch, source and destination address, protocol, source and destination port, ingress port, then the six features, then the label. The first eight identify the flow and are never shown to the model - they exist so that a detection can name a port to block.

FeatureMeaningWhy it helps
pkt_ratepackets per secondfloods are loud — but so is a busy client
byte_ratebytes per secondseparates many tiny packets from a big download
avg_pkt_sizebytes per packetattack packets are small
durationseconds the flow has existedattack flows are short-lived
pair_flow1 if replies come backreal conversations get answered; floods do not
port_src_countdistinct sources on that portmany sources on one port suggests an attack — though a shared uplink looks the same

Is 567 rows enough?

For this problem, yes. An image classifier needs millions of examples because one photo is 150,000 numbers and the model must discover its own features and learn millions of weights. Here one example is six numbers we chose ourselves, and the trained Decision Tree is a single threshold. Learning one number from 567 rows is comfortable.

The real limitation is not quantity but variety. The training set contains one attack rate, one topology and one traffic mix. That is exactly why the Decision Tree fails on a quieter attack — the same way a cat detector trained only on black cats fails on a white one, not for lack of black cats.

What each layer could not do, and what we did instead

These are the load-bearing workarounds. If something breaks later, it will probably be one of these.

What to show as proof

The honest framing first, because it is also the strongest one: no detector here is better than another in general. Each one is a different point on a trade-off between catching attacks and blocking innocent traffic. What can be proved is which point each method reaches, and that two of them reach better points than the others. Saying this out loud is what separates a considered project from one that quotes a single accuracy figure.

Do not lead with accuracy

Against the low-rate attack the Decision Tree records 0 true positives, 0 false positives, 77 false negatives and 490 true negatives - an accuracy of 86.4% while catching nothing at all. Roughly 86% of flows are normal, so a detector that flags nothing scores 86% for free. Lead with recall, false positives, and packets reaching the victim.

The four pieces of evidence, in order of strength

  1. The mechanism, not a statistic. Open src/DecisionTree.h: the entire trained model is if (byte_rate <= 116465.5) return 0;. The full-rate attack runs at ~345,000 B/s and is caught; the quiet one runs at ~13,900 B/s and falls on the wrong side, so every attack flow is called normal. This explains the failure rather than merely reporting it, and nobody can argue with it.
  2. It is not just a weak model. A Random Forest trained on the same data fails identically (recall 0.00), while a second unsupervised method, Isolation Forest, catches the attack like K-Means. The pattern holds across both families, which answers the obvious objection that a stronger supervised model would have coped.
  3. The network outcome. Packets reaching the victim is free of the imbalance and denominator problems that affect recall: 4,396 with no protection, 4,396 with the Decision Tree, 1,394 with the hybrid, 651 with K-Means. The tree delivering exactly as many packets as no defence at all is the single most damning number in the project.
  4. The frontier. results/frontier.png shows false positives against recall for every setting of both new rules, with plain K-Means and the Decision Tree marked for reference. At the same false-positive level the cost rule reaches 0.51 recall where the hybrid reaches 0.31. That is the comparison, stated properly: not "better", but "better at this operating point".

A live demo that makes the point in ninety seconds

  1. Run NoProtection in the GUI. Run Until 18 s, then Fast. Watch the switch-to-victim link light up and stay lit.
  2. Run KMeans the same way. The attackers turn red, the switch announces the block, and the victim link goes quiet while the access link stays busy - the flood is arriving and being destroyed at the switch.
  3. Run LowRate_DT. Nothing turns red. Nothing is blocked. The victim link stays lit. That is the failure, visible.
  4. Run LowRate_Cost with the penalty at 30,000. Blocking resumes.

Then show the three charts. The live demo proves the system works; the charts prove it works repeatedly, across five random seeds.

Questions worth having an answer ready for

  • "Why not a public dataset?" The model runs inside the switch, so it has to be trained on features the switch can measure; public captures describe flows with different features entirely. And the central experiment needs an attack at a rate we choose, which a fixed dataset cannot provide.
  • "567 rows is tiny." One example is six numbers and the trained tree is a single threshold - quantity was never the constraint. Variety is: one attack rate, one topology. That narrowness is exactly what the low-rate experiment exposes.
  • "Did you test on your training data?" The dataset was collected on seed 0 and the experiments use seeds 0-4, so run 0 shares its normal traffic. Runs 1-4 are independent, and the low-rate attack never appeared in training at all.
  • "Isn't recall unfair to the hybrid?" Yes, partly - every second it waits for corroboration counts as a miss, and blocking removes the very traffic being counted, so the detectors' recalls rest on slightly different denominators. That is why packets-reaching-the-victim is reported alongside.

Where the results come from

Every number in the report traces back to a file you can open. experiments.sh runs each configuration five times with different random seeds and writes results/experiments.csv; sweep.sh varies the attack strength into results/sweep.csv. The plotting scripts read those and produce the charts. Nothing is typed in by hand.

Each simulation also writes OMNeT++'s own result files under simulations/results/ — scalars per run, which is where the scripts read detections, false positives and packet counts from. Those are large and regenerated by any run, so they are not committed.
