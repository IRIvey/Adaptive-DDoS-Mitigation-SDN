Architecture & Build Notes

Comparative Analysis of Supervised and Unsupervised ML for DDoS Detection in SDN

An OMNeT++ simulation in which an SDN controller detects distributed denial-of-service traffic with two different machine learning approaches and blocks the attacker automatically. This document records what has been built, how each piece works, and what remains.

OMNeT++ 6.0.2 INET 3.8.5 OpenFlow (CoRE-RG) scikit-learn 1.9 D:\IUT\3-2\DP2\SDN-DDoS-ML

What the project asks

A Decision Tree learns from labelled examples of both normal and attack traffic. K-Means never sees an attack at all — it learns only what normal looks like, and flags anything far from it. Both can block an attacker. The question is what happens when the attack is one neither model was trained on.

That framing matters because it is the part the original reference project never tested. Showing that a model detects the attack it was trained on proves very little; showing how each approach behaves on an attack pattern absent from training is a real result, in either direction.

Runtime architecture

Hosts send traffic through an OpenFlow switch toward a victim server. The switch reports to the controller, which extracts features, classifies each flow, and installs a drop rule when a flow is judged hostile. The loop that matters is the one that closes: detection has to result in a rule that changes what the switch does next.

The two-phase pipeline

Training happens in Python, where scikit-learn is; detection happens in C++, inside the simulator. These are separate programs that never run at the same time, so the trained model has to cross the boundary as source code. train.py writes two C++ headers that are compiled into the controller.

This is why both models were chosen. A Decision Tree becomes nested if/else statements; K-Means becomes a handful of centroid coordinates and a distance check. Neither needs a machine learning library at simulation time — which is what keeps the C++ side small enough to finish.

Feature design, and why it is per-flow

The reference project computed statistics per switch per time window. That can say “this switch is under attack” but not which port to block — which is why it needed a separate hand-written rule to find the attacker. Here every row describes a single flow, so a positive classification already names the switch, source and ingress port that the drop rule needs.

It also makes the metrics mean something. A false positive is a legitimate flow that got blocked, which connects directly to the throughput and packet-loss numbers. With window-level rows, a false positive is just a misclassified time window and connects to nothing.

Feature Meaning Why it separates attack from normal

Each feature is individually defeatable, which is the point. No single one is a giveaway, so the models must combine them — and the identity columns (switch_id, src_ip, in_port) travel alongside without ever being fed to the model.

The two models

The difference is not the algorithm, it is what each one is allowed to see during training.

The methodology detail that decides whether this is valid

K-Means needs a distance threshold, and where that number comes from is the whole ballgame. It is taken as the 99th percentile of the distances of the normal training data only. If it were tuned on data containing attacks, the model would be quietly supervised and the comparison would be meaningless. An examiner will ask about this, so it is stated explicitly in train.py.

On the attack it was trained on, the Decision Tree is excellent: 0.92 recall and not one legitimate flow blocked. On an attack twenty-five times quieter that it never saw, it catches nothing — and the victim receives exactly as many packets as it would with no protection at all. K-Means holds at 0.98 across both, because knowing what normal looks like does not depend on having met the attack.

It pays for that with roughly seven to nine legitimate flows blocked per run. That is the trade the project set out to measure, and it is visible in the network rather than asserted in a table. Blocks lapse after ten seconds, so a false positive costs a bounded amount of traffic.

The reason is legible in the generated model, which is the whole argument for exporting it as source rather than as an opaque file. The entire trained tree is one comparison — byte_rate <= 116465.5. The full-rate attack runs at about 345,000 B/s and sits above it; at one-fifth rate it is about 69,000 B/s and sits below, so every attack flow is classified normal. The model learned a single number, and any attack on the wrong side of it is invisible.

A detail worth carrying into the write-up: at 1/5 rate the Decision Tree lets 20,210 packets reach the victim, roughly twice as many as at full rate. It defends worse against the weaker attack, because against the loud one it at least blocked something.

Accuracy is the wrong headline here

Facing the low-rate attack the Decision Tree records TP 0, FP 0, FN 77, TN 490 — an accuracy of 86.4% while catching nothing at all and delivering exactly as many packets to the victim as no defence. About 86% of flows are normal, so flagging nothing scores 86% for free.

There is also a subtlety in recall itself: successful mitigation removes the traffic being measured. In the low-rate runs the Decision Tree recorded 567 flow observations and K-Means only 419, because K-Means blocked the attackers and the flood stopped being reported. The two recalls therefore rest on different denominators. The metric free of this problem is the network outcome — packets reaching the victim — which is why it gets its own figure.

Three corrections worth recording

Every one of these produced plausible-looking numbers that meant nothing, and each was caught by inspecting the dataset rather than by the simulation failing.

Packet size gave the game away. An early synthetic set had normal packets at 400–1400 bytes and attack packets at 54–300, with no overlap, so one threshold solved it and both models scored 100%. The tell was feature importance: avg_pkt_size at 1.000, every other feature at zero.

pair_flow read 1 for everything. Flows were keyed without transport ports, so a client's answered echo traffic and its one-way telemetry merged into a single flow that inherited the replies. Ports are now part of the key — which is what a flow means in OpenFlow terms anyway.

Detection latency came out negative. K-Means raised a false positive before the attack had started, and latency was being measured from the first detection of any kind. It now measures to the first correct detection.

The missing flow statistics, and how they were solved

The upstream model ships no flow-statistics message — no OFP_Stats_Request, no flow-stats reply — and OF_FlowTableEntry stores only creationTime, lastMatched and the two timeouts. There is no packet counter and no byte counter anywhere in the flow table, so three of the six features had nothing to read.

The obvious response is to patch the model and maintain a fork. That turned out to be unnecessary. OF_Switch::handleMessage is virtual and its members are protected, so DDoSSwitch subclasses it and does everything from our own project: taps every data-plane frame, keeps per-flow counters, and drops blocked traffic before the base class ever forwards it. The report reaches the controller on the OpenFlow vendor channel (OFPT_VENDOR), which the controller already forwards to apps as a PacketExperimenter signal. The vendored model is an unmodified checkout.

Two things fell out of building it this way. First, with flow rules properly installed the controller sees numPacketIn = 7 out of roughly 41,000 packets — a detector reading packet-in events would be almost completely blind, so switch-side measurement is required rather than merely tidier. Second, a flow-mod cannot express a drop at all: the switch reads an output port straight out of the matched entry and has no notion of an empty action list, and disablePorts() only affects flooding, not forwarding. The drop is therefore implemented in DDoSSwitch and driven by a DDoSBlockCommand.

Software stack

Versions are pinned deliberately. The OpenFlow model targets OMNeT++ 6.0.2 with INET 3.8.5, and newer releases of either break it — INET 4.x restructured the source tree entirely, and OMNeT++ 6.2 and later ship a stricter clang toolchain.

Things that cost time, recorded so they are not repeated

  • The NED path needs both openflow/src and openflow/scenarios; the scenarios folder is its own package root.
  • The DLL directories must be on PATH, or Windows cannot resolve libINET.dll when the simulation loads.
  • The bundled 7za.exe in 6.0.2 is old and rejects the -bso0 -bsp0 -bb0 quiet flags with “incorrect command line”.
  • modifiedInetFiles/openflow-inet-hack.patch targets INET 2.x paths and does not apply to 3.8.5. It is not needed to compile; revisit only if IP auto-configuration misbehaves on switch interfaces.
  • The opp_featuretool errors about missing tutorial and showcase NED packages during the INET build are harmless.

Reproducing the ML side

cd ml
python make_synthetic.py --out ../data/train.csv
python make_synthetic.py --out ../data/test_lowrate.csv --intensity 0.2 --seed 7
python train.py --train ../data/train.csv --test ../data/test_lowrate.csv

When the simulator starts producing real data, the same train.py command runs against it unchanged — only the input file differs.

What is left

Two things were planned and are not in the build, both for reasons worth stating rather than working around.

A real SYN flood. INET's TCP does not work over this path at all — a connection establishes and then the first data request never reaches the server application. This was verified against the flood-everything controller, so it is not the OpenFlow forwarding. Normal client traffic uses UDP echo instead, which gives the same bidirectional property. A genuinely spoofed half-open SYN flood would additionally need a raw-IP injector that INET does not provide; claiming one would be dishonest, so the second attack type is a low-rate flood — which turned out to be the more informative experiment anyway.

Source spoofing. Same reason. Instead, port_src_count gets its variation honestly from the access switch, which puts several real hosts on one ingress port.

Natural extensions from here: more attack intensities to find where each model breaks, more seeds for tighter confidence intervals, and a larger topology to see whether the result holds when a port carries far more mixed traffic.
